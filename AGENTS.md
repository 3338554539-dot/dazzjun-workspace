# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

## Durable prototype decisions

- The top application bar must not show the macOS red, yellow, and green traffic-light controls on any page. Keep the Dazzjun工作台 title aligned directly to the bar's left padding.
- Phase 2 is data-driven: module status, dashboard metrics, and histories must come from the persisted Zustand workspace store rather than static display values.
- Phase 7.2 replaces the platform-based inspiration entrances with two same-level spaces: 收藏灵感 and 我的笔记. 收藏灵感 unifies Douyin, Xiaohongshu, and web records; platform is source metadata rather than a category or navigation boundary.
- Phase 3 growth metrics, habit tracking, annual summaries, global search, and backup exports must be derived from the unified workspace store; AI features remain provider-agnostic interfaces until a model is explicitly configured.
- Phase 4 AI Assistant must remain local-first by default: deterministic insights may use persisted workspace data, while external models, cloud sync, encryption, identity, and recovery stay behind replaceable interfaces. Keep knowledge links, memories, AI reports, exports, and restores in the unified versioned data model.
- V4.5 establishes the durable Dazzjun brand mark as a geometric `D + orbit + light point`. Reuse the same mark for the top-bar lockup, hero, personal identity, favicon, and PWA icons; top-level command controls use the custom glass-node visual language instead of default system icons.
- Phase 5 defines the intelligence pipeline as `Perception -> Memory -> AI Core -> Action`. Keep perception derived from the unified local workspace, separate short/long/knowledge memory, route through a provider-agnostic AI Router, and require explicit confirmation before any future external model receives user data. Proactive notifications may suggest actions but must not execute decisions automatically.
- V5.0 starts every fresh workspace without demo records and removes only known seed IDs during persisted-data migration. The theme system is config-driven and persisted separately under `dazzjun.theme.v1`; Cosmic remains the default, with Forest and Ocean as active alternatives. Keep backup import/export in Command Center rather than restoring the removed top-bar archive/input controls.
- V5.1 makes theme selection global through `ThemeProvider`: every official or custom theme must drive the hero, top bar, seven modules, AI Core, cards, forms, borders, icons, shadows, and motion from one complete token configuration. Keep the five official themes (Cosmic, Forest, Ocean, Minimal White, Future City), generate custom palettes entirely on-device from uploaded wallpaper pixels, and persist only the selected theme and user-created themes under `dazzjun.theme.v1`; never upload wallpaper data.
- V6.0 makes Dazzjun account-gated and API-first. Runtime workspace records, themes, growth data, and AI memory belong to the authenticated user and must never use shared browser persistence as their source of truth. Local development uses the SQLite adapter; production uses the Worker + D1 adapter and the same user-scoped contract. Existing V5 browser data may be read only through the explicit one-time import flow and then saved into the current account.
- V6.1 keeps external collections as account-scoped structured assets: `content`, full `url`, optional `image`, and `categoryId`. Every account receives the six stable default categories 设计、AI、摄影、穿搭、音乐、商业; only account-owned custom categories may be renamed or deleted. External cards use native new-tab links so the workspace state remains intact, and legacy inspiration payloads are normalized and written back after account load.
- V7.0 Phase 4 keeps long-term AI Memory in the dedicated account-scoped `ai_memory` table, separate from workspace records and chat messages. Only explicit create/delete actions may change it; the fixed types are preference, goal, habit, identity, and insight, and every API/context query derives ownership from the authenticated session.
- V7.0 Phase 5 persists AI context authorization per account, keeps recoverable short-term chat in `ai_conversations` partitioned by `conversation_id`, and stores at most one daily insight per account and Shanghai calendar date. Chat history must never be copied into `ai_memory` automatically; any future memory extraction requires a separate explicit flow.
- V7.0 Phase 5.5 makes AI context authorization default-on and persistent per account: the first authorization read creates an enabled record, while an explicit user opt-out remains disabled across refreshes. Authorization copy must describe account-level personal context, never a one-session grant.
- V7.0 Phase 5.5 frontend persistence uses only the authenticated AI APIs for authorization, `daily_assistant` chat history, and today's insight. `/ai-core` is the durable AI Core location and must survive Session restoration and browser refresh without falling back to Overview; chat history must never use localStorage.
- Todo tasks keep planned execution and final due dates separate: the shared `getTodayTasks()` selector and only `scheduleDate === today` determine Today Plan membership, Today progress, growth rings, daily AI context, and Today task notifications, while `deadline` remains the due date shown in the Todo timeline. Creating or editing `startAt` must synchronize `scheduleDate`; editing only `deadline` must preserve it. Legacy `dueAt` records must normalize without data loss.
- Phase 7.1 external capture remains Worker-only: canonical `platform` is `douyin`, `xiaohongshu`, or `web`. Phase 7.2 keeps legacy `portal` values only for record/backup compatibility and never uses them for UI grouping. Preserve legacy `content`/`image` aliases, let account-owned category choices override AI tags, and never fetch third-party page metadata from the browser.
- Phase 5.6 keeps AI persistence and authorization unchanged while making DeepSeek requests bounded and retryable: chat uses a 60-second provider timeout, daily insight uses 90 seconds, and only transient timeout/network/rate-limit/5xx failures retry once after one second. Surface provider, network, timeout, and D1 persistence failures distinctly.
- The Overview inspiration moment must come from the authenticated user's existing `inspirations` records through `/api/inspiration/random`. Its selection is stable per user and Shanghai calendar day, never uses a static quote as real content, and shows an explicit empty state without adding persistence tables.
- Phase 7.2.1 never persists branded placeholder assets as captured covers. Worker capture follows validated redirects and prefers platform JSON/video cover data before Open Graph and Twitter images; collection cards fall back in `cover -> image -> platform placeholder` order, while Overview uses only real `cover`/legacy `image` data and otherwise shows its empty-cover state.
- Authentication startup has three explicit states: `loading`, `authenticated`, and `unauthenticated`. Keep the current route behind a stable loading screen until `/api/auth/session` resolves or reaches its five-second timeout; never render the login gateway from the initial `user === null`. PWA updates must activate only after the user chooses the update action, never from an unconditional Service Worker `controllerchange` reload.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.
